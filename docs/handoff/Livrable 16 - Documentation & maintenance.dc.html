2. Guide administrateur — procédures clés

  • Traiter une demande d'inscription — Établissements → filtre « En attente » → ouvrir la fiche → vérifier contact, formule souhaitée et message → configurer l'abonnement (§ facturation) → « Valider ». La validation est bloquée tant que l'abonnement n'est pas encaissé (RG14) : 409 facture_non_payee renvoie vers l'écran facturation.
  • Fixer un tarif et facturer — Abonnement & facturation → sélectionner l'établissement → formule (essai gratuit, abonnement mensuel / annuel −10 %, ou paiement à la vue avec plafond) → saisir le tarif → générer la facture (Non payée) → à réception du paiement, « Marquer payée » → reçu HTML téléchargeable (F2026-NNNNNN attribué par FacturationService sous verrou $queryRaw FOR UPDATE, TVA 20 %, RG14, RG18).
  • Gérer le sponsoring — attribuer un niveau (Premium / Gold / Silver) par ville, catégorie ou mot-clé ; la rotation d'affichage est équitable entre sponsors de même niveau (RG19).
  • Modérer un avis — écran Avis → chip « En attente » ou « Signalés » → décision (publier / masquer) avec motif ; la note moyenne et le nombre d'avis sont recalculés dans la même transaction Prisma (RG06–RG08) ; entrée d'audit horodatée (RG26).
  • Valider une modification de fiche — file « Modifications de fiche à valider » → écran « Vérifier une modification » → aperçu du diff (DiffPanel) + aperçu profil avec champ surligné → Approuver / Modifier / Refuser ; la publication rend la modification visible dès le rendu SSR suivant, la clé de cache fiche:{slug} étant purgée (RG20, RG27).
  • CRM Clients — pipeline de prospection commerciale (Nouveau → Transformé / Perdu) ; une transformation crée le compte + la fiche établissement et déclenche la commission à la première facture (RG17, RG18).
  • Utilisateurs & rôles (avenant n° 3, RG25) — écran Secrétariat pour créer, suspendre, réinitialiser le mot de passe des comptes secrétariat ; la réinitialisation détruit les sessions Passport du compte cible dans Redis et envoie un mot de passe temporaire. Les rôles admin / commercial / établissement ont un périmètre fixe (lecture seule).
  • Journal d'audit (avenant n° 3, RG26) — filtres par rôle et sévérité ; lecture seule (aucune méthode d'écriture n'est déclarée dans le controller : POST / PATCH / DELETE → 404) ; purge automatique à 3 ans par le conteneur scheduler (@nestjs/schedule).
  • Blog (avenant n° 3, RG27) — décider les articles en attente (approuver / refuser + mise à la une) ; l'approbation purge la clé de cache articles:public. La gestion des catégories (ajouter / retirer) et la validation des propositions de nouvelles catégories envoyées par les autres profils se fait dans Contenu du site.
  • Contenu du site — FAQ (ajout / réordonnancement / édition), page « À propos » (histoire, mission, valeurs, coordonnées), catégories du blog. Chaque écriture purge la clé de cache publique correspondante.

3. Guide établissement & secrétaire — procédures clés

  • Compléter sa fiche — Ma fiche → informations, photos (téléversement contrôlé côté API — MIME, poids, re-encodage sharp, écrites dans le volume storage), équipements, équipe, tarifs, chiffres clés, FAQ, vidéo, autres projets, réseaux sociaux ; l'enregistrement crée une proposition soumise à validation via FicheProposalService (RG20). La fiche n'est visible qu'avec une formule active (RG13).
  • Suivre son activité — tableau de bord : demandes, vues, avis, leads à relancer ; écran Statistiques pour le détail par période.
  • Gérer ses leads (CRM) — chaque demande de contact devient un lead ; compléter la fiche de besoin (FC-1 → FC-11) affine le score (RG22, borné 0–10 par LeadService) ; faire avancer le lead dans le pipeline (6 statuts), programmer des relances, conclure en « inscrit » (avec acompte) ou « perdu » (avec motif) — RG21. Un lead peut aussi être créé manuellement (« + Nouveau lead »).
  • Abonnement & factures — consulter la formule active, les vues du profil et l'historique des factures (lecture seule) ; les tarifs sont fixés avec le conseiller (RG14).
  • Blog (avenant n° 3) — activer le blog dans les paramètres du compte ; rédiger un article → soumission → attente d'approbation par l'administration (RG27). Si aucune catégorie de la liste ne convient, choisir « Autre catégorie… » : le nom saisi part en proposition pour validation admin.
  • Paramètres du compte — dans la sidebar, cliquer sur son tile de profil (bas de la barre) : modifier les coordonnées (nom + e-mail, avec confirmation du mot de passe actuel), changer son mot de passe (8 caractères minimum), téléverser une photo de profil.
  • Portées de la secrétaire — accès limité aux fiches, contacts et avis délégués (RG05, nav fixe Tableau de bord · Demandes · Fiches en 5e passe) ; elle traite les leads via son établissement mais ne peut ni les supprimer ni les exporter — ces droits appartiennent à l'Admin Client (RG23) — 403 côté API sans exception.

4. Runbook d'exploitation

Procédures opérationnelles, condensé du livrable 14 v2.5. Toutes s'exécutent sur le VPS Hostinger KVM via SSH (utilisateur deploy, clé, jamais root, membre du groupe docker), depuis /srv/ecoles360 ; les commandes destructrices sont proscrites en production (RG14, RG26). La production étant conteneurisée, PM2 n'existe plus : les redémarrages sont assurés par les politiques Docker et les healthchecks.

# Déployer une version → tag Git → CI construit et pousse les images → deploy.sh git tag v1.x.y && git push --tags # le VPS ne compile jamais : il télécharge des images ./deploy.sh <sha> # écrit TAG=<sha> puis : # docker compose pull && docker compose up -d --remove-orphans # le conteneur api applique « prisma migrate deploy » à son démarrage # Revenir en arrière (rollback) → redéployer le tag précédent tail -n 5 /srv/ecoles360/deploiements.log # historique des SHA mis en service ./deploy.sh <sha-precedent> # Redéployer UN SEUL composant → sans toucher aux autres services docker compose pull api && docker compose up -d --no-deps api # front, MySQL, Redis, Nginx intacts docker compose up -d --no-deps web # correction d'interface seule docker compose restart worker # relance BullMQ sans couper l'API # Consulter l'état et les journaux docker compose ps # état + santé des sept services docker compose logs -f --tail=100 api # journaux applicatifs (pilote json-file, rotation 10 Mo) docker stats # CPU / mémoire par conteneur # Restaurer la base (RTO 4 h) → depuis le dump chiffré Hostinger Object Storage mc cp hostinger/ecoles360-backup/backup-AAAAMMJJ.sql.gz.gpg . docker compose up -d mysql gpg --decrypt backup-AAAAMMJJ.sql.gz.gpg | gunzip \ | docker compose exec -T mysql mysql ecoles360_prod docker compose up -d api # rejoue les migrations éventuelles au démarrage # Vérifier la santé → même sonde que le HEALTHCHECK Docker curl -f https://ecoles360.com/api/v1/health # version + profondeur des 5 files + Prisma # Traitements planifiés (sinon @Cron du conteneur scheduler) docker compose restart scheduler # relance les @Cron (purges, backup, rappels) docker compose run --rm api node dist/cli.js purge:donnees # anonymisation 12 mois manuelle (09-08)
Incident courant Diagnostic → action
Notifications / factures en retardFile BullMQ engorgée → docker compose restart worker ; profondeur exposée par /api/v1/health.
Erreurs 5xx après déploiementConsulter docker compose logs -f api et docker compose ps (service non healthy) → rollback immédiat par ./deploy.sh <sha-precedent>, puis analyse hors ligne.
Un seul composant à corrigerLivrer l'image du service concerné puis docker compose up -d --no-deps <service> — les autres services, les sessions Redis et les files BullMQ ne sont pas interrompus (livrable 14 v2.5 §4.1).
Disque saturéRotation des journaux par le pilote json-file (10 Mo × 5), purge des images inutilisées par docker image prune -af --filter "until=720h" (faite par deploy.sh), contrôle du quota médias par offre (RG16).
Certificat TLS expirantRenouvellement Let's Encrypt automatique par certbot sur l'hôte ; en cas d'échec, sudo certbot renew puis docker compose exec nginx nginx -s reload.
Reprise complète (RTO 4 h)Reprovisionner un VPS Hostinger KVM via hPanel → playbook Ansible bootstrap.yml (Docker + Compose + certbot + ufw + fail2ban seulement) → restaurer le dump dans le volume mysql_data + rsync du volume storage → réémettre les certificats → ./deploy.sh <dernier-sha> (aucune compilation).

5. Plan de maintenance

Type Périmètre Engagement
CorrectiveAnomalies (dont réserves R-01, R-02 du livrable 15 v2.5)Bloquant < 4 h (RTO), majeur < 2 j, mineur au prochain jalon ; chaque correctif accompagné d'un test de non-régression Jest, Vitest ou Playwright (L13 v2.5 §6).
PréventiveDépendances, images de base, sécurité, sauvegardesMises à jour mensuelles (NestJS patch, Prisma, Passport, BullMQ, dépendances npm via pnpm audit) et remontée mensuelle des images de base (node:20-alpine, mysql:8, redis:7, nginx) pour absorber les correctifs amont ; test de restauration trimestriel, revue des accès et du journal d'audit RG26.
AdaptativeEnvironnement (Node.js LTS, MySQL 8 → 9, Ubuntu, Redis)Suivi des versions LTS Node.js (20 → 22) par simple changement d'image de base, migration validée d'abord sur le staging conteneurisé via GitHub Actions ; playbook Ansible re-testé.
ÉvolutiveNouvelles fonctions (avenants, Lot 2)Matching lead ↔ offre V1.1 (R-03), RTL arabe, avenant n° 2 « compte parent léger » (RG24 — inscription e-mail + mot de passe requise pour déposer un avis, historiques de recherche et de contact, sans tableau de bord) — chacun suit la même démarche : cahier des charges → conception → tests → recette.

Les évolutions majeures sont formalisées en avenants au cahier des charges, répercutés dans les livrables concernés avec un historique des révisions (méthode éprouvée sur les avenants n° 1 — v2.1 — et n° 3 — v2.3, sur la migration de stack — v2.4 — et sur la correction d'architecture NestJS + Docker — v2.5). L'avenant n° 2 porte sur le compte parent léger (RG24) : la piste d'une vérification par code OTP envoyé en WhatsApp ou SMS a été étudiée puis abandonnée au profit d'une inscription e-mail + mot de passe, plus simple à exploiter et sans coût de passerelle.

6. Clôture de la démarche & transfert

Les seize livrables sont produits, validés et exportés hors-ligne ; les avenants n° 1 (CRM leads, v2.1) et n° 3 (console d'administration & CMS, v2.3) sont intégrés au modèle ; la migration Laravel → Next.js + Hostinger VPS KVM (v2.4) puis la correction d'architecture NestJS 10 + React 18/Vite avec conteneurisation Docker de la production (v2.5) ont été menées sur L7/L10/L11/L12/L13/L14/L15/L16 en septembre 2026 ; la recette est prononcée avec réserves mineures (livrable 15 v2.5). L'ensemble constitue un cahier des charges complet et traçable — de l'analyse de l'existant à l'exploitation.
