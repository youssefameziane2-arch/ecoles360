Version 2.5 · Septembre 2026 · S'appuie sur les livrables 4–6 (design system, maquettes — avenants n° 1 et n° 3), 7 v2.5 (architecture NestJS + React/Vite, production conteneurisée) et 11 v2.5 (contrat d'API NestJS) · Prépare le livrable 13 (stratégie de tests)

1. Périmètre et décisions structurantes

Le front-end est une web app mobile first (livrable 9 §hors-périmètre : pas d'app native en V1). NestJS ne rendant pas de HTML, le front redevient une application séparée (dossier web/, image Docker dédiée) qui dialogue avec l'API par HTTP. Deux modes de rendu cohabitent dans ce même dépôt : SSR ciblé pour le site public — les ~8 000 fiches doivent être indexables avec leur balisage schema.org LocalBusiness (RG03, RG08) — et SPA pure pour les trois back-offices, authentifiés et hors référencement (livrable 7 §1, décision de rendu). Chaque choix ci-dessous est minimal : aucun framework CSS, aucun store global superflu — l'état de vérité est l'API, le style de vérité est le design system.

Brique Choix retenu — justification
SocleReact 18 · Vite 5 · TypeScript 5 · Node.js 20 LTS (livrable 7 §1). En développement, pnpm --filter web dev sert le front et proxifie /api vers l'API NestJS ; en production, vite build produit les assets et le serveur SSR, embarqués dans l'image ecoles360-web (livrable 14).
RoutageRoutage par fichier Vike (vite-plugin-ssr) — les dossiers src/pages/public/, src/pages/espace/{etablissement,secretariat,commercial}/ et src/pages/admin/ portent chacun leur layout et leur garde (§3). Découpage de bundle natif par route ; un parent n'embarque jamais le bundle d'un back-office (§6).
RenduSSR sur le site public · SPA sur les back-offices — les pages de listing, de fiche, d'avis et de blog public déclarent ssr: true : le serveur de rendu appelle l'API sur le réseau interne Docker, produit le HTML complet (SEO — RG08) puis l'hydrate. Les écrans connectés déclarent ssr: false et sont rendus entièrement côté client (§4).
État serveurTanStack Query 5 pour tout — une clef par ressource, invalidations explicites après mutation (§4). En SSR, la donnée est préchargée côté serveur puis déshydratée dans le HTML (HydrationBoundary), ce qui évite un aller-retour au premier rendu. Pas de Redux : l'état applicatif restant (session, filtres d'URL) tient dans l'URL et le contexte de session.
MutationsUne seule voie : appels HTTP /api/v1/* encapsulés dans useMutation. Les Server Actions de la v2.4 disparaissent : tout passe par le contrat REST documenté (livrable 11), donc par les mêmes DTO, guards et services que n'importe quelle intégration tierce — aucun chemin d'écriture privilégié.
AuthentificationSession serveur Passport + cookie (livrable 11 §2) — POST /auth/login ouvre la session, GET /auth/me la résout au démarrage et alimente un SessionProvider React. Front et API étant servis sous la même origine par nginx, le cookie HttpOnly / SameSite=Lax part seul — ni CORS, ni jeton stocké en localStorage. Le jeton CSRF est lu dans son cookie et renvoyé en en-tête à chaque mutation.
FormulairesReact Hook Form avec des règles de saisie alignées sur les DTO class-validator du livrable 11 §5 (téléphone marocain, message ≤ 1 000 caractères, note 1–5, consentement requis) ; le 422 de l'API reste l'arbitre et ses erreurs sont re-projetées champ par champ (§6).
CartographieLeaflet + OpenStreetMap chargé par React.lazy et rendu après hydratation — carte des résultats et mini-carte de la fiche, jamais incluses dans le HTML rendu côté serveur.
Styles & composantsDesign system écoles360 chargé via _ds_bundle.js (tokens CSS + 46 composants) dans le layout racine (§5). Aucune couleur ni taille hors tokens ; aucun composant UI réécrit.

Découpage par surface, aligné sur les quatre espaces des maquettes : un dossier src/pages/<surface>/<écran>/ par écran, qui compose des composants du design system et lit ses données par un hook React Query. 3. Routage et gardes par surface

Les routes reprennent une à une les navigations des maquettes validées. Les gardes sont doubles : côté serveur, les Guards NestJS restent seuls juges (livrable 11 §2) ; côté front, elles évitent d'afficher un écran vide — un guard Vike vérifie la session résolue par GET /auth/me sur espace/* et admin/* (sinon redirection /connexion?retour=…), le layout de surface contrôle le rôle attendu, et pour le secrétariat la SidebarNav ne montre que les sections dont la portée est active (RG05) — une portée révoquée reste refusée par l'API même si l'écran est atteint à la main. Après POST /auth/login, la redirection suit le rôle renvoyé : etablissement → /espace/etablissement, secretariat → /espace/secretariat, commercial → /espace/commercial, superadmin → /admin (vérifiable avec les comptes de démonstration du livrable 10).

4. Intégration de l'API et gestion d'état

Une seule voie d'accès : HTTP vers /api/v1/*. En SSR, le serveur de rendu appelle l'API sur le réseau interne Docker (http://api:3000) et relaie le cookie de session entrant ; côté client, le même client HTTP tape la même origine publique, le cookie HttpOnly partant seul. Ni CORS, ni jeton en localStorage, ni chemin d'écriture privilégié : la SPA et le rendu serveur passent par les mêmes DTO, guards et services que n'importe quelle intégration tierce. Les erreurs suivent le format d'API (livrable 11 §1) et sont traduites en toasts ou états d'erreur par un handler unique :

// src/api/client.ts — client HTTP unique (SSR et navigateur) const BASE = import.meta.env.SSR ? process.env.API_INTERNAL_URL // http://api:3000/api/v1 — réseau interne Docker : "/api/v1"; // même origine, routé par nginx export async function apiFetch<T>(path: string, init?: RequestInit): Promise<T> { const res = await fetch(`${BASE}${path}`, { ...init, credentials: "include", // cookie de session Passport (HttpOnly) headers: { "content-type": "application/json", "x-csrf-token": readCsrfCookie(), // double-submit (livrable 11 §2) ...(init?.headers ?? {}), }, }); const body = await res.json().catch(() => ({})); if (res.ok) return body.data as T; // enveloppe {data, meta, links} const { code, message, details } = body ?? {}; if (res.status === 401) return redirectToLogin(); // session expirée ou révoquée (RG25) if (res.status === 403) toast.erreur(message ?? "Accès non autorisé."); // rôle ou portée (RG05) if (res.status === 409) toast.avertissement(message); // conflit métier : // plafond_vue_atteint, reponse_existante, // abonnement_deja_actif, facture_non_payee, // proposition_deja_en_attente (msg L11) if (res.status === 429) toast.avertissement("Trop de tentatives. Réessayez dans quelques minutes."); throw new ApiError(code, message, details, res.status); // 422 : laissé aux formulaires (mapping par champ, §6) } // src/hooks/useSubmitFicheProposal.ts — mutation React Query (remplace la Server Action v2.4) export function useSubmitFicheProposal() { const qc = useQueryClient(); return useMutation({ mutationFn: (payload: FicheProposalPayload) => apiFetch("/mon-espace/fiche/propositions", { method: "POST", body: JSON.stringify(payload) }), onSuccess: () => { // RG20, RG27 — rien n'est public avant approbation qc.invalidateQueries({ queryKey: ["fiche"] }); // le bandeau « en attente de validation » apparaît qc.invalidateQueries({ queryKey: ["propositions-fiche"] }); toast.succes("Votre modification a été soumise à validation."); }, }); }

Conventions TanStack Query — une clé par module, calquée sur les ressources du livrable 11 ; chaque mutation invalide exactement les clés qu'elle périme. Pour les contenus servis en SSR (fiche, blog, FAQ, À propos), l'invalidation est double : la clé Query côté client, et la clé de cache Redis côté API que le service concerné supprime dans la même transaction (livrable 11 §1) — c'est elle qui fait que le prochain rendu serveur voit la nouvelle version.

Aucune écriture optimiste sur les opérations à invariants (facturation, validation de fiche, décision d'article) : on affiche l'état confirmé par le serveur, seule vérité comptable et éditoriale (RG14, RG20, RG27).

États systématiques — chaque écran traite ses quatre états avec les composants dédiés du DS : chargement (Skeleton du DS, jamais de page blanche ni de spinner plein écran — en SSR la page part déjà peuplée), vide (EmptyState avec action), erreur (frontière d'erreur par route + Toast portant le message de l'API), indisponible (ProfileUnavailable quand la fiche repasse en fiche de base, RG13). Les formats passent tous par lib/formats.ts (Intl fr-MA) : virgule décimale (★ 4,8), espace fine des milliers (8 420), « 2 500 MAD/mois », dates courtes françaises.

6. Qualité : formulaires, accessibilité, performance

  • Formulaires — React Hook Form porte des règles de saisie écrites en miroir des DTO class-validator du livrable 11 §5 : mêmes contraintes (téléphone marocain, message ≤ 1 000 caractères, note 1–5, consentement requis), mêmes messages français. La validation côté client n'est qu'un confort d'ergonomie : le 422 du ValidationPipe reste l'arbitre, et ses details[] sont re-projetés champ par champ sous les Input du DS via setError. Boutons désactivés pendant l'envoi (état isPending de la mutation), double soumission impossible côté UI, idempotence côté serveur.
  • Accessibilité (AA) — cibles tactiles ≥ 44 px et contrastes garantis par les tokens du DS ; focus visible, modales à piège de focus, formulaires entièrement labellisés, navigation clavier sur FilterBar, Tabs, Kanban (drag & drop clavier via @dnd-kit) et DataTable ; la DataTable bascule en cartes empilées sous 720 px (breakpoints du DS).
  • Performance — budget du bundle public initial ≤ 180 Ko gzip. Le découpage par route de Vike isole le code des back-offices (pages/espace/, pages/admin/) : il n'est jamais téléchargé sur le site public. Leaflet, le kanban et l'éditeur de fiche sont importés via React.lazy après hydratation ; les images sont servies aux dimensions demandées par l'API (re-encodage sharp, livrable 11 §5) avec ratio réservé en CSS — zéro décalage de mise en page. Objectif LCP < 2,5 s sur mobile 4G milieu de gamme, mesuré en CI par Lighthouse sur les trois routes publiques clés (accueil, résultats, fiche).
  • Référencement du site public — pages publiques rendues côté serveur par Vike : title et description renvoyés par le onBeforeRender de chaque route, URL en slugs, sitemap.xml et robots.txt servis par l'API depuis la liste des fiches validées, données structurées schema.org LocalBusiness injectées dans le HTML de la fiche. C'est la raison d'être du SSR ciblé retenu au livrable 7 §1 : sans lui, les ~8 000 fiches ne seraient pas indexables (RG08).
  • Préparation arabe / RTL — conformément au livrable 9 (hors V1) : chaînes centralisées dans lib/i18n.ts, propriétés CSS logiques (margin-inline-start…) dans tout style écrit au niveau front, formats via Intl. Aucune traduction livrée en V1.

Prochaine étape — Livrable 13 : stratégie de tests (Jest + Supertest + Prisma test DB côté API — invariants d'abonnement, de paiement à la vue, de commission, de validation de fiche et de scoring lead (RG21–RG23) —, Vitest + React Testing Library + MSW côté composants, Playwright pour les cinq parcours acteur, matrice RG ↔ tests).
