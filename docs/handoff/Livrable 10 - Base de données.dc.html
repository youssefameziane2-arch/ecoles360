1. Rappel du MPD et conventions Prisma

Le modèle physique est celui du livrable 8 (v2.3) : 23 relations métier en 3e forme normale (dénormalisations contrôlées note_moy / nb_avis), toutes en InnoDB / utf8mb4_unicode_ci, clés primaires BIGINT UNSIGNED auto-incrémentées. S'y ajoutent la table users (compte applicatif, rôle porté par role_id) et la table password_reset_tokens ; ni les sessions ni les files n'ont de table SQL — les sessions Passport sont persistées dans Redis 7 (connect-redis), ce qui les rend révocables (RG25), et les files BullMQ vivent dans le même Redis. S'y ajoute enfin une table de paramètres de facturation globaux introduite au §5. Les tarifs propres à chaque établissement (abonnement, prix par vue, sponsoring) vivent sur leurs tables respectives, jamais dans un barème public. Le fichier unique prisma/schema.prisma remplace les 31 migrations Laravel de la v2.3 ; les commandes prisma migrate dev (développement) et prisma migrate deploy (staging / production) génèrent et appliquent les migrations SQL versionnées. En production, prisma migrate deploy est exécuté au démarrage du conteneur api, avant le bootstrap NestJS : la base est donc toujours à la version de l'image déployée, et un retour au tag précédent redéploie une image dont les migrations sont déjà appliquées (livrable 14). Les conventions ci-dessous garantissent la correspondance stricte modèle Prisma ↔ MPD.

Convention Règle adoptée
Nommage des tablesModèles Prisma en PascalCase ; tables physiques en snake_case pluriel via @@map("etablissements"), colonnes via @map("cree_le"). Les noms physiques restent identiques au MLD (etablissements, demande_contacts, journal_audits, etablissement_niveau).
Clésid BigInt @id @default(autoincrement()) @db.UnsignedBigInt ; clés étrangères en {entite}_id BigInt @db.UnsignedBigInt + relation nommée avec onDelete: Cascade | Restrict | SetNull (livrable 8 §7).
HorodatagesNoms français du MPD conservés (cree_le, recue_le, maj_le…) via @map ; Prisma DateTime @default(now()) @db.Timestamp(0) ; les modèles en insertion seule (audit, traces) omettent délibérément @updatedAt.
ÉnumérationsBlocs enum Prisma projetés en ENUM MySQL natif ; valeurs sans accents ni majuscules (creche, publie, vue_sponsorisee), consommées directement en TypeScript côté services (livrable 11) — plus besoin d'un Enum PHP dupliqué.
FULLTEXT & CHECKFULLTEXT déclaré via @@fulltext([nom, description]) (feature preview fullTextIndex activée dans le generator) ; les contraintes CHECK — non gérées par le DSL Prisma — sont ajoutées par un fichier SQL supplémentaire dans le même dossier de migration (prisma migrate exécute tout *.sql présent).
Moteur & charsetDatasource mysql ; le serveur MySQL 8 est configuré (my.cnf) en default-storage-engine=InnoDB + character-set-server=utf8mb4 + collation-server=utf8mb4_unicode_ci — appliqués à toute table créée par Prisma.
RéversibilitéChaque migration versionnée dans prisma/migrations/ ; retour arrière contrôlé par prisma migrate resolve + migration inverse manuelle pour les reprises de données (§2.12) ; la chaîne complète est validée par prisma migrate reset --skip-seed puis pnpm --filter api db:seed en CI, sur la MySQL 8 réelle levée par docker-compose.test.yml (livrable 14).

Le schéma est écrit dans un ordre topologique — référentiels d'abord, pivot Etablissement ensuite, puis ses satellites ; Facture après Abonnement, PaiementVue et Sponsoring pour ses rattachements optionnels ; Prospect, Relance et Commission (etablissement_id nullable) ferment la chaîne commerciale ; les modèles du CRM leads de l'avenant n° 1 (Lead, LeadSuivi) closent la séquence ; l'avenant n° 3 ajoute Role, les champs JSON de la page profil, les entités éditoriales (Article, FaqItem, PageCms) et enrichit JournalAudit / Avis / PropositionFiche. La table de correspondance ci-dessous conserve la numérotation 01–31 des migrations Laravel v2.3 pour la traçabilité par règle de gestion — chaque numéro correspond désormais à un modèle (ou à un enrichissement de modèle) dans le fichier unique schema.prisma.

4. Stratégie d'import open data (≈ 8 000 fiches)

L'annuaire est amorcé par les listes publiques d'établissements privés autorisés (ministère de l'Éducation nationale / data.gov.ma, exports CSV par académie). L'import est une commande NestJS idempotente (ImportEtablissementsCommand, même binaire CLI que les seeders) exécutée par pnpm --filter api import:etablissements en local, ou dans un conteneur éphémère en environnement déployé — le fichier CSV étant déposé dans le volume storage ; le traitement se fait en 6 étapes, par lots de 500 lignes dans une transaction Prisma chacun ; les fiches créées naissent en statut en_attente, source open_data, non rattachées à un compte (RG04) — la visibilité publique passe par la validation admin par lots.

1 · COLLECTE
Exports CSV MEN chargés tels quels en table de staging import_brut + hash de ligne
→
2 · NETTOYAGE
Trim, casse, téléphones +212, mapping vers les 6 types ENUM et les villes du référentiel
→
3 · DOUBLONS
Clé nom normalisé + ville, puis similarité (Levenshtein ≤ 2) ; cas ambigus en file admin
→
4 · SLUGS
slugify(nom-ville), suffixe -2, -3… en cas de collision — URL SEO stables (livrable 9)
→
5 · GÉOLOC
Géocodage Nominatim (1 req/s, cache Redis) ; défaut = centroïde de la ville, à affiner à la revendication
→
6 · INSERTION
statut en_attente, source open_data, aucun abonnement ni tarif tant que non revendiquée ; validation admin par lots

Figure 1 — Pipeline d'import open data : du CSV brut à la fiche en attente de validation.

docker compose run --rm api node dist/cli.js import:etablissements /storage/imports/men-2026.csv --dry-run # 8 214 lignes lues · 7 962 importables · 187 doublons fusionnés · 65 rejets (rapport CSV) docker compose run --rm api node dist/cli.js import:etablissements /storage/imports/men-2026.csv

La commande est rejouable sans doublon : chaque ligne source est identifiée par son hash (stocké en staging) ; une ligne déjà importée est ignorée, une ligne modifiée est proposée en mise à jour. Le mode --dry-run produit le rapport complet (importables, doublons, rejets motivés) sans écriture — c'est le livrable de recette de l'import (livrable 15).

5. Paramètres de facturation globaux

Les seules valeurs globales sont des constantes réglementaires ou commerciales communes à tous les clients ; le modèle ParametreFacturation les rend modifiables depuis le back-office admin, lues via cache applicatif Redis (invalidé à chaque modification), toute modification étant une action sensible journalisée (RG15). Aucun tarif d'établissement n'y figure : le prix de l'abonnement et le prix par vue sont saisis directement sur Abonnement / PaiementVue, propres à chaque client (RG14).

6. Procédures d'exploitation

6.1 — Sauvegarde quotidienne

  • docker compose exec -T mysql mysqldump --single-transaction --routines --triggers chaque nuit à 03 h 00 (job BullMQ backup déclenché par le conteneur scheduler via @Cron, livrable 7 §2) — le dump est produit depuis un conteneur éphémère, sans binaire MySQL installé sur l'hôte et sans verrouillage des tables InnoDB (le site reste servi).
  • Rotation : 7 sauvegardes quotidiennes, 4 hebdomadaires, 12 mensuelles ; archives compressées et chiffrées (GPG), copiées hors du serveur applicatif (stockage objet).
  • Contrôle d'intégrité hebdomadaire : restauration à blanc sur conteneur MySQL jetable + comptage des tables critiques (etablissements, factures, abonnements) — une sauvegarde non testée n'est pas une sauvegarde.
  • Les photos (volume Docker storage) suivent une synchronisation incrémentale rsync séparée — la base ne stocke que les chemins ; l'instantané fait partie du même job BullMQ.

6.2 — Restauration (objectifs V1 : RPO 24 h · RTO 4 h)

  1. Passage en maintenance : docker compose stop api web worker scheduler + activation d'une page d'attente servie par le conteneur nginx.
  2. Restauration du dump sur une base temporaire (jamais directement sur la base de production).
  3. Contrôles : comptages des tables critiques, dernière facture émise (séquence numero), intégrité des clés étrangères (SET FOREIGN_KEY_CHECKS = 0/1 et vérification).
  4. Bascule par renommage de bases, purge du cache Redis (FLUSHDB ciblé sur les clés applicatives, pas sur les files BullMQ ni sur les sessions), puis docker compose up -d api web worker scheduler.
  5. Journal d'incident (cause, données perdues éventuelles, durée) ; exercice de restauration trimestriel documenté en recette (livrable 15).

6.3 — Purge et minimisation (loi 09-08)

Conformément aux durées déclarées à la CNDP (livrable 9), le conteneur scheduler — même image que l'API, commandé différemment (livrable 7 §2) — déclare quatre tâches récurrentes par @Cron ; chaque exécution est journalisée (nombre de lignes traitées) dans JournalAudit via AuditService — la file BullMQ maintenance exécute effectivement les traitements dans le conteneur worker, pour permettre les retries et l'observabilité. Un seul exemplaire du conteneur scheduler tournant, aucune tâche ne peut être déclenchée deux fois.

Job BullMQ Fréquence Traitement
purge:demandesQuotidien 02 h 00Anonymise les demandes traitées depuis plus de 12 mois : parent_nom → « Anonymisé », parent_tel et message effacés ; les compteurs statistiques sont conservés (RG16).
purge:tracesQuotidien 02 h 30Agrège evenement_traces en statistiques journalières (par fiche, type, jour) puis supprime les lignes brutes de plus de 12 mois (RG10, volumétrie livrable 8 §7).
purge:auditHebdomadaire dim. 04 h 00Supprime les entrées journal_audits de plus de 3 ans (RG26 — avenant 3) ; les factures et propositions rattachées ne sont jamais purgées.
abonnements:rappelsQuotidien 08 h 00Notification d'échéance à J-7 (RG14) — pas une purge, mais planifiée au même endroit.
backup:quotidienQuotidien 03 h 00Sauvegarde §6.1. Les factures ne sont jamais purgées (conservation comptable 10 ans).
// api/src/maintenance/maintenance.scheduler.ts — conteneur « scheduler » (livrable 7 §2) import { Injectable } from "@nestjs/common"; import { Cron } from "@nestjs/schedule"; import { InjectQueue } from "@nestjs/bullmq"; import { Queue } from "bullmq"; @Injectable() export class MaintenanceScheduler { constructor(@InjectQueue("maintenance") private readonly maintenance: Queue) {} @Cron("0 2 * * *") purgeDemandes() { return this.maintenance.add("purge:demandes", {}); } @Cron("30 2 * * *") purgeTraces() { return this.maintenance.add("purge:traces", {}); } @Cron("0 4 * * 0") purgeAudit() { return this.maintenance.add("purge:audit", {}); } @Cron("0 3 * * *") backupQuotidien(){ return this.maintenance.add("backup:quotidien", {}); } @Cron("0 8 * * *") rappels() { return this.maintenance.add("abonnements:rappels", {}); } // RG14 }
