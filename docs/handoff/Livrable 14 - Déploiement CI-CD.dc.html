1. Environnements cibles

Quatre environnements décrits par quatre fichiers Compose versionnés dans le dépôt — docker-compose.dev.yml, .test.yml, .staging.yml, .prod.yml. C'est le premier gain de la conteneurisation : la pile logicielle n'est plus décrite dans une procédure d'installation, elle est déclarée et identique partout ; seules changent les données, l'échelle et les accès. Le domaine ecoles360.com a été acheté chez Hostinger : les enregistrements A / AAAA sont configurés dans hPanel pour pointer vers l'IP publique du VPS ; le sous-domaine staging.ecoles360.com partage la même adresse.

2. Topologie de production — Docker Compose sur VPS Hostinger KVM

Cible retenue : Hostinger VPS KVM 2 minimum (2 vCPU, 8 Go RAM, 100 Go SSD NVMe) sous Ubuntu 24 LTS, accès root SSH par clé, IPv4 + IPv6 dédiées. Le serveur n'héberge plus qu'un moteur Docker et un fichier Compose : tout le reste — Node, MySQL, Redis, Nginx — vit dans des images. PM2 disparaît de la production, remplacé par les politiques de redémarrage Docker (restart: unless-stopped) et les healthchecks de chaque service. Sept services composent la production :

La conteneurisation isole les runtimes ; l'indépendance fonctionnelle entre parties du site vient des modules NestJS — un module par domaine métier, avec son controller, son service, ses DTO et ses guards. Les deux mécanismes sont complémentaires et c'est leur combinaison qui permet de modifier une partie sans toucher aux autres (livrable 7 §2).

2.2 — Dockerfiles multi-étages

Les deux images sont construites en plusieurs étapes : les dépendances de développement et les sources TypeScript ne survivent pas à l'étape finale. L'image applicative tourne en utilisateur non-root et déclare un HEALTHCHECK — c'est lui que Compose interroge avant de considérer le service comme disponible, et c'est lui qui déclenche le redémarrage automatique en cas de blocage.

# api/Dockerfile — NestJS 10 FROM node:20-alpine AS deps WORKDIR /app RUN corepack enable COPY api/package.json api/pnpm-lock.yaml ./ RUN pnpm install --frozen-lockfile FROM node:20-alpine AS build WORKDIR /app RUN corepack enable COPY --from=deps /app/node_modules ./node_modules COPY api/ ./ RUN npx prisma generate && pnpm build # → dist/main.js, dist/worker.js, dist/scheduler.js RUN pnpm prune --prod # ne garde que les dépendances d'exécution FROM node:20-alpine AS runtime WORKDIR /app ENV NODE_ENV=production RUN addgroup -S app && adduser -S app -G app # utilisateur non-root COPY --from=build --chown=app:app /app/node_modules ./node_modules COPY --from=build --chown=app:app /app/dist ./dist COPY --from=build --chown=app:app /app/prisma ./prisma USER app EXPOSE 3000 HEALTHCHECK --interval=30s --timeout=5s --retries=3 --start-period=40s \ CMD node -e "fetch('http://127.0.0.1:3000/api/v1/health').then(r=>process.exit(r.ok?0:1))" CMD ["node","dist/main.js"]
# web/Dockerfile — React 18 + Vite (SSR ciblé du site public) FROM node:20-alpine AS build WORKDIR /app RUN corepack enable COPY web/package.json web/pnpm-lock.yaml ./ RUN pnpm install --frozen-lockfile COPY web/ ./ RUN pnpm build # vite build → dist/client + dist/server RUN pnpm prune --prod FROM node:20-alpine AS runtime WORKDIR /app ENV NODE_ENV=production PORT=4000 RUN addgroup -S app && adduser -S app -G app COPY --from=build --chown=app:app /app/node_modules ./node_modules COPY --from=build --chown=app:app /app/dist ./dist COPY --from=build --chown=app:app /app/server.js ./server.js USER app EXPOSE 4000 HEALTHCHECK --interval=30s --timeout=5s --retries=3 \ CMD node -e "fetch('http://127.0.0.1:4000/sante').then(r=>process.exit(r.ok?0:1))" CMD ["node","server.js"] # sert le SSR public + les assets de la SPA

3. Intégration continue — tests puis publication des images

À chaque push et chaque pull request, deux jobs parallèles rejouent la pyramide du livrable 13 v2.5 sur une base MySQL 8 et un Redis 7 réels. Les images ne sont construites qu'ensuite, dans un job qui dépend du succès des précédents, puis poussées sur GitHub Container Registry (ghcr.io) et taguées par SHA de commit. Une image existe donc si, et seulement si, ses tests sont passés — et le VPS ne compile jamais : il ne fait que télécharger des artefacts déjà éprouvés, ce qui supprime du serveur de production la chaîne de build, ses dépendances de développement et son risque d'échec à mi-parcours.

4. Déploiement continu — par tag d'image

Déployer ne consiste plus à reconstruire l'application sur le serveur, mais à désigner le tag d'image à exécuter. Le fichier .env.prod du VPS porte une variable TAG ; le workflow de déploiement l'écrit au SHA validé, puis lance docker compose pull et docker compose up -d. Les conteneurs sont recréés dans l'ordre des dépendances, chacun n'entrant en service qu'une fois son healthcheck au vert. Déclenché par GitHub Actions sur main (staging) et sur tag vX.Y.Z (production), par SSH sur un utilisateur deploy non-root membre du groupe docker.

# deploy.sh — exécuté sur le VPS Hostinger par l'utilisateur deploy set -euo pipefail cd /srv/ecoles360 SHA="$1" echo "TAG=$SHA" > .env.tag # le tag devient l'unique variable de version docker compose -f docker-compose.prod.yml --env-file .env.tag pull docker compose -f docker-compose.prod.yml --env-file .env.tag up -d --remove-orphans # ↑ api applique « prisma migrate deploy » à son démarrage (L10 v2.5 §2) # ↑ chaque service n'est déclaré prêt qu'après son healthcheck docker compose -f docker-compose.prod.yml ps # contrôle : tous les services « healthy » curl -fsS https://ecoles360.com/api/v1/health > /dev/null echo "$SHA" >> /srv/ecoles360/deploiements.log # journal des tags déployés (rollback, §4.2) docker image prune -af --filter "until=720h" # purge les images de plus de 30 jours

4.1 — Redéployer un seul composant sans toucher aux autres

C'est l'objectif même de la conteneurisation pour ce projet. Chaque service étant une unité de déploiement autonome, on peut remplacer l'API sans interrompre le front, la base, le cache ni le proxy :

# Reconstruire et redémarrer UNIQUEMENT l'API — web, mysql, redis et nginx ne bougent pas docker compose up -d --no-deps --build api # Variante « image déjà publiée en CI » (cas nominal en production) : docker compose pull api && docker compose up -d --no-deps api # Autres cas d'usage du même mécanisme : docker compose up -d --no-deps web # livrer une correction d'interface seule docker compose restart worker # relancer les consommateurs BullMQ sans couper l'API docker compose exec nginx nginx -s reload # recharger le proxy après renouvellement TLS

L'option --no-deps est la clé : sans elle, Compose recréerait aussi les services dont api dépend (mysql, redis), c'est-à-dire précisément ceux qu'il ne faut pas redémarrer. Les sessions Passport et les files BullMQ vivant dans Redis (livrable 11 §2), le remplacement du seul conteneur api ne déconnecte personne et ne perd aucun job. Le rappel du §2 vaut ici pleinement : Docker garantit qu'un redémarrage n'en entraîne pas d'autres, et le découpage en modules NestJS garantit qu'une évolution de domaine n'oblige pas à en toucher un autre.

4.2 — Retour arrière

Le rollback est la même opération que le déploiement, avec le tag précédent — les images antérieures restant disponibles sur ghcr.io et en cache local sur le VPS. Le fichier deploiements.log donne l'historique des SHA mis en service :

tail -n 5 /srv/ecoles360/deploiements.log # retrouver le SHA précédent ./deploy.sh <sha-precedent> # redéploiement du tag antérieur

Une réserve à connaître : les migrations de base ne reculent pas avec l'image. Toute migration doit donc rester compatible avec la version précédente de l'application (ajout de colonne nullable, jamais de suppression dans la même livraison) ; une suppression de colonne se fait en deux livraisons successives. Cette règle est inscrite au guide de contribution (livrable 16).

4.3 — Staging : même VPS, projet Compose distinct

Le staging tourne sur le même serveur, mais dans un projet Compose séparé (-p ecoles360-staging) décrit par docker-compose.staging.yml : conteneurs, réseau et volumes portent le préfixe du projet, la base s'appelle ecoles360_staging et le server_name nginx dédié est staging.ecoles360.com. C'est nettement plus propre que la cohabitation « bare-metal » de la v2.4, où les deux environnements partageaient la même instance MySQL, le même Redis et le même gestionnaire de processus, et où une erreur de variable d'environnement pouvait faire écrire le staging dans la base de production. Ici, l'isolation est structurelle : deux projets Compose ne partagent ni réseau, ni volume, ni conteneur.

# Déploiement du staging — mêmes images, projet et données distincts docker compose -p ecoles360-staging -f docker-compose.staging.yml pull docker compose -p ecoles360-staging -f docker-compose.staging.yml up -d docker compose -p ecoles360-staging exec api npx prisma migrate reset --force docker compose -p ecoles360-staging run --rm api node dist/cli.js db:seed # données anonymisées # Les deux projets cohabitent sans se voir : docker compose -p ecoles360 ps # production docker compose -p ecoles360-staging ps # staging (volumes ecoles360-staging_mysql_data, …)

5. Sauvegarde, supervision et plan de reprise (RPO 24 h · RTO 4 h)

  • Sauvegarde base (RPO 24 h) — job BullMQ backup:quotidien planifié à 03 h par le conteneur scheduler (@Cron, livrable 10 §6.3). Le dump est produit depuis un conteneur éphémère, sans binaire MySQL installé sur l'hôte : docker compose exec -T mysql mysqldump --single-transaction --routines --triggers ecoles360_prod | gzip -9 | gpg --encrypt --recipient backup@ecoles360.com, puis dépôt sur Hostinger Object Storage (S3-compatible, disponible depuis hPanel, mêmes datacenters), avec repli documenté vers un fournisseur S3-compatible tiers (Wasabi ou Backblaze B2). Rétention : 30 quotidiennes, 4 hebdomadaires, 12 mensuelles. Les factures F2026-NNNNNN et les journaux d'audit restent en base pour leur durée légale (10 ans, 3 ans — RG14, RG26).
  • Sauvegarde fichiers — rsync incrémental quotidien du volume storage (photos des fiches — RG16, images d'articles — RG27, affiches vidéo, visuels des autres projets) vers le même dépôt objet. La base ne conserve que les chemins (livrable 10 §2.12) ; le volume étant nommé, il survit à tout remplacement d'image — c'est un gain net sur la v2.4, où les médias vivaient dans un dossier partagé entre releases.
  • Reprise (RTO 4 h) — procédure runbook (livrable 16), sensiblement raccourcie par la conteneurisation : (1) reprovisionnement d'un VPS Hostinger KVM 2 depuis hPanel avec l'image Ubuntu 24 LTS de base ; (2) exécution du playbook Ansible bootstrap.yml, désormais réduit à l'installation de Docker Engine, du plugin Compose, de certbot, de fail2ban et d'ufw — il n'installe plus Node, PM2, MySQL ni Redis, tous devenus des images ; (3) restauration : docker compose up -d mysql puis gpg --decrypt … | docker compose exec -T mysql mysql ecoles360_prod, et rsync du volume storage ; (4) réémission des certificats Let's Encrypt ; (5) ./deploy.sh <dernier-sha> — aucune compilation, seulement des docker pull ; (6) vérification par la check-list de recette (livrable 15). Exercice de restauration réalisé sur le staging chaque trimestre.
  • Supervision — sonde externe UptimeRobot (hors du VPS) sur GET /api/v1/health, qui retourne 200 avec la version, la profondeur des cinq files BullMQ et le statut de la connexion Prisma — c'est aussi la commande du HEALTHCHECK Docker (§2.2), donc une seule définition de « en bonne santé » pour la sonde externe et pour l'orchestrateur. Alertes SMS et e-mail au-delà de 2 minutes de latence ou 3 échecs consécutifs. Exploitation manuelle par docker compose ps, docker compose logs -f api et docker stats.
  • Journaux — chaque conteneur écrit sur stdout ; le pilote json-file est configuré globalement (max-size: 10m, max-file: 5) dans /etc/docker/daemon.json, ce qui remplace pm2-logrotate. Les logs nginx sont montés sur l'hôte pour rester lisibles par fail2ban et logrotate. Ils se corrèlent par l'identifiant de trace posé par l'interceptor de l'API (livrable 11 §2). Les actions sensibles (validation, suspension, modération, permission, publication CMS, réinitialisation de mot de passe) restent en outre tracées dans le journal d'audit métier (RG15, RG26).

6. Sécurité de la mise en service

  • Chiffrement — HTTPS obligatoire (Let's Encrypt, certbot sur l'hôte avec renouvellement automatique ; /etc/letsencrypt monté en lecture seule dans le conteneur nginx, rechargé par docker compose exec nginx nginx -s reload en deploy hook) ; TLS 1.2 / 1.3 uniquement ; redirection 80 → 443 ; HSTS (max-age=31536000; includeSubDomains) ; en-têtes Content-Security-Policy, X-Content-Type-Options, Referrer-Policy, Permissions-Policy posés par nginx et par helmet côté API (livrable 11 §5).
  • Authentification — Passport + express-session sur connect-redis : cookie HttpOnly + Secure + SameSite=Lax, CSRF double-submit, hachage Argon2id. Le domaine ecoles360.com couvre le front et l'API — nginx route /api vers api et le reste vers web, donc même origine, pas de CORS. Les sessions vivant dans Redis sont révocables — utilisées lors de la suspension d'un compte et de la réinitialisation de mot de passe (RG25).
  • Secrets — variables sensibles (DATABASE_URL, SESSION_SECRET, mots de passe des seeders, jetons Hostinger Object Storage, clé GPG de sauvegarde) dans /srv/ecoles360/.env.prod (chmod 600, propriétaire deploy), chargé par env_file ; le mot de passe root MySQL passe par un secret Docker monté en fichier plutôt que par une variable d'environnement — jamais dans le dépôt, jamais dans l'image. Rotation semestrielle documentée au runbook (livrable 16).
  • Réseau — ufw restreint l'hôte aux ports 22/tcp (SSH par clé, PermitRootLogin no, PasswordAuthentication no), 80/tcp et 443/tcp — inchangé par rapport à la v2.4. Côté conteneurs, seul nginx publie des ports ; api, worker, scheduler et web ne sont joignables que sur le réseau interne ecoles360_net, et MySQL comme Redis ne publient que sur 127.0.0.1. fail2ban couvre SSH et les logs nginx montés sur l'hôte.
  • Durcissement des images — images finales alpine minimales, exécution en utilisateur non-root, aucune dépendance de développement ni source TypeScript embarquée (§2.2), tags immuables par SHA (jamais :latest en production, ce qui interdit toute dérive silencieuse de version). Les images de base sont remontées mensuellement pour absorber les correctifs de sécurité amont (plan de maintenance, livrable 16).
  • Limitation de débit — @nestjs/throttler adossé à Redis (livrable 11 §5) : avis et demandes 5 par heure et par IP, connexion et réinitialisation de mot de passe 5 par minute ; le staging reste protégé par Basic Auth nginx et fermé aux moteurs (X-Robots-Tag: noindex, nofollow).
  • Loi 09-08 — les purges du livrable 10 §6.3 (anonymisation des demandes à 12 mois, agrégation des traces à 12 mois, purge du journal à 3 ans) tournent en production dans le conteneur scheduler ; chaque exécution laisse une entrée d'audit horodatée (RG26).

Prochaine étape — Livrable 15 : recette (procès-verbal, scénarios de bout en bout par acteur — parent, établissement, secrétaire, admin / Super Admin, commercial — reprenant les parcours du livrable 13 v2.5 §4, dont la conversion d'un lead CRM et la décision d'un article, et les critères d'acceptation du livrable 3, joués sur le staging conteneurisé staging.ecoles360.com déployé par le présent livrable).
