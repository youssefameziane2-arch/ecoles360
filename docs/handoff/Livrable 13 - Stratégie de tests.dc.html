Stratégie de tests

Pyramide de tests du projet : unitaires et intégration Jest + Supertest côté API NestJS (services et controllers, base MySQL 8 réelle pilotée par Prisma), Vitest + React Testing Library + MSW côté composants, parcours Playwright de bout en bout — avec la matrice de traçabilité RG01–RG27 ↔ tests qui sert de socle à la recette.

Version 2.5 · Septembre 2026 · S'appuie sur les livrables 10 v2.5 (schema.prisma + seeders en commandes NestJS), 11 v2.5 (modules src/modules/**, douze services, Guards, avenants n° 1 et n° 3) et 12 v2.5 (front-end React 18 + Vite — SSR ciblé du site public, SPA des back-offices) · Prépare les livrables 14 (déploiement CI-CD conteneurisé) et 15 (recette)

1. Stratégie et environnement de test

Le risque du produit reste concentré dans les invariants d'argent et de confiance : abonnement et paiement à la vue (RG11–RG14), facturation légale et commissions (RG14, RG18), validation Super Admin des fiches (RG20, RG27), modération (RG06–RG08), portées déléguées (RG05), CRM leads de l'établissement (RG21–RG23 — avenant n° 1, données nominatives soumises à la loi 09-08) et console d'administration (RG25 rôles / permissions / réinitialisation de mot de passe, RG26 journal d'audit immuable, RG27 circuits éditoriaux CMS — avenant n° 3). La pyramide place donc l'essentiel de l'effort au plus près de ces invariants — tests rapides, déterministes, exécutés à chaque commit — et réserve le bout en bout aux parcours par acteur rejoués en recette (livrable 15).

  • Base de test = MySQL 8 réelle, jamais SQLite — les comportements testés (verrous $queryRaw FOR UPDATE de ViewBillingService et FacturationService, ENUM MySQL natif, contraintes CHECK, index FULLTEXT, collation utf8mb4) sont ceux du moteur de production (livrable 10 v2.5 §2.0). MySQL 8 et Redis 7 sont lancés par un docker-compose.test.yml local (ports isolés) ; en CI (livrable 14) ils sont fournis en tant que services GitHub Actions.
  • Base pilotée par Prisma — un globalSetup Jest appelle prisma migrate deploy puis la commande de seed du L10 v2.5 (SeedCommand : rôles, villes, niveaux-filières, comptes et données de démonstration, leads, CMS, audit — jamais l'import open data des ~8 000 fiches). Les suites se partagent la base par worker Jest (--runInBand pour les suites de concurrence) ; chaque test écrit dans un sous-arbre de données factory disjoint pour éviter les collisions.
  • Jest côté API — l'outil par défaut de NestJS (il remplaçait Pest en v2.4 sous la forme de Vitest) : même pyramide, mêmes cibles, mais adossé au conteneur de dépendances du framework. Les tests unitaires montent un module réduit par Test.createTestingModule() et injectent les vrais services avec un PrismaService pointé sur la base de test ; les tests d'intégration HTTP passent par Supertest sur l'application Nest complète — pipes, guards, interceptors et filtres inclus, donc le contrat exact du livrable 11.
  • Front testé contre le contrat — Vitest + RTL + MSW, inchangés. Les mocks MSW reproduisent l'enveloppe {data, meta, links} et les erreurs {code, message, details} du livrable 11 §1 ; leurs fixtures sont générées depuis la spécification OpenAPI publiée sur /api/docs — un écart de contrat casse les tests front avant d'atteindre la préproduction.
  • Ordres de grandeur cibles — couverture de branches ≥ 90 % sur api/src/modules/**/*.service.ts, ≥ 85 % sur les guards (api/src/common/guards/ et api/src/modules/**/guards/ — RG05, RG23, RG25), ≥ 80 % sur les controllers ; une douzaine de parcours Playwright, pas plus — un parcours par risque, pas par écran.
BOUT EN BOUT — PLAYWRIGHT
Cinq parcours par acteur sur staging seedée (§4) — lents, peu nombreux, rejoués en recette
INTÉGRATION HTTP — JEST + SUPERTEST + PRISMA TEST DB
Le contrat d'API du livrable 11 endpoint par endpoint sur l'application Nest complète : statuts, enveloppe, guards et portées, ValidationPipe, throttling, messages français
UNITAIRES — JEST (SERVICES NESTJS) · VITEST + RTL + MSW (COMPOSANTS)
Les invariants au plus près du code : ViewBillingService, FacturationService, SubscriptionService, CommissionService, ProspectService, LeadService, ReviewModerationService, ContactRequestService, FicheProposalService, ArticleWorkflowService, AuditService, CmsService · formats fr-MA, hooks, formulaires, gardes — exécutés à chaque commit

2. Tests back-end (Jest + Supertest + Prisma test DB)

2.1 — Unitaires : les douze services transactionnels (livrable 11 §4)

  • ViewBillingService — comptage des vues facturables en paiement à la vue, jamais au-delà de plafond_mensuel ; aucun comptage pour un établissement en abonnement ou en essai gratuit ; job BullMQ plafondAtteint déclenché à l'unité du plafond (RG12).
  • FacturationService — numérotation séquentielle F2026-NNNNNN sans trou ni doublon (verrou FOR UPDATE testé en concurrence, §2.3) ; TVA 20 % ; origine exclusive abonnement / vue / sponsoring (RG14).
  • SubscriptionService — unicité de l'abonnement actif (RG11) ; remise annuelle −10 % correctement calculée ; expiration → retour à la fiche de base ; rappel J-7 déclenché par le conteneur scheduler (test de la méthode @Cron abonnements:rappels, livrable 10 §6.3).
  • CommissionService — commission calculée à la génération de facture (statut a_valider) ; passage à reglee impossible sans validation Direction explicite (RG18).
  • ProspectService — transitions du pipeline (nouveau → … → transformé / perdu) ; transformation crée un compte + une fiche liés au prospect (RG17).
  • LeadService (avenant 1) — scoring aux bornes : urgence 0–4 + adéquation budget 0–3 + complétude 0–3, score toujours dans 0–10 y compris après ajustement manuel (±3 refusé s'il sort des bornes) ; recalcul à chaque mise à jour de la fiche de besoin ; transitions du pipeline 6 statuts — passage à perdu refusé sans raison_perte, passage à inscrit fixe converti_le et accepte acompte_mad ; création automatique depuis une demande de contact avec fiche de besoin pré-remplie (RG21, RG22).
  • ReviewModerationService — publie / rejete + recalcul de note_moy et nb_avis dans la même transaction Prisma (RG08) ; signalement → retour en file (RG07) ; entrée d'audit écrite par AuditService (RG15, RG26).
  • ContactRequestService — consentement obligatoire (RG09) ; création automatique du Lead lié à la demande (RG21) ; jobs BullMQ mail + alerts émis (établissement + secrétariat).
  • FicheProposalService (avenant 3) — unicité d'une proposition en attente par établissement, testée sous concurrence (§2.3) — un second dépôt reçoit une ConflictError("proposition_deja_en_attente") ; annulation par l'auteur tant que la proposition est en attente ; publication directe pour le Super Admin, sinon file ; les badges de plateforme (sponsorisé, vérifié, premium, note, nombre d'avis) sont retirés de tout payload client, quel que soit le rôle (RG20, RG27).
  • ArticleWorkflowService (avenant 3) — transitions brouillon → en_attente → approuvé / refusé, slug unique, horodatages soumis_le / publie_le renseignés ; un compte non Super Admin ne peut atteindre approuvé par aucun chemin ; la mise en avant reste sans effet public hors statut approuvé ; désactivation du blog du compte (blog_actif = false) conserve les articles déjà approuvés (RG27).
  • AuditService (avenant 3) — immuabilité : aucune méthode publique de mise à jour ni de suppression n'est exposée, seule la création via le client Prisma étendu ($extends) est utilisée ; le rôle de l'acteur est figé au moment de l'écriture (RG26) — un changement de rôle ultérieur ne réécrit jamais l'entrée. Purge à trois ans testée sur données forgées de plus de 36 mois.
  • CmsService (avenant 3) — FAQ : réordonnancement en une requête (liste d'identifiants ordonnée), l'ordre est recalculé de façon contiguë ; PageCms : blocs typés validés par DTO class-validator ; chaque écriture purge les clés de cache publiques (faq:public, pages:a-propos) via le CacheModule Redis et laisse une entrée d'audit (RG26, RG27).

2.2 — Intégration HTTP (Supertest) : le contrat, endpoint par endpoint

L'application Nest est instanciée une fois par suite (Test.createTestingModule({ imports: [AppModule] }).compile() puis app.init()), avec le ValidationPipe, les guards, l'interceptor de sérialisation et le filtre d'exceptions réels — c'est donc bien le contrat du livrable 11 qui est éprouvé, pas une réimplantation. Les sessions sont forgées par un agent Supertest authentifié via POST /api/v1/auth/login, qui conserve le cookie pour les requêtes suivantes.

  • Visibilité — seules les fiches validées sortent des listes publiques ; fiche en_attente ou suspendue → 404 (RG03) ; sponsorisées servies en tête (RG19).
  • Autorisations — pour chaque route protégée : 401 sans session, 403 mauvais rôle, 403 portée absente ou révoquée (RG05) ; compte suspendu rejeté par le SessionGuard ; un commercial ne lit que ses prospects affectés (RG17) ; un établissement ne lit jamais les données d'un autre — leads compris (RG23) ; suppression et export de leads : 403 pour la secrétaire, 200 pour l'Admin Client (LeadGuard, avenant 1) ; le Super Admin n'a aucune route vers le détail nominatif des leads, seulement vers les agrégats (livrable 11 §2, §3.4).
  • Avenant 3 — console d'administration — 403 sur /admin/utilisateurs pour tout non Super Admin (RoleGuard, RG25) ; création limitée au rôle secrétariat, 422 si etablissement_rattache_id manquant ; 409 sur une permission unitaire visant un rôle à périmètre fixe ; réinitialisation de mot de passe : entrée d'audit de sévérité avertissement écrite, sessions Redis du compte cible détruites (le cookie précédent renvoie 401 au coup suivant), ancien mot de passe jamais restitué ; refus d'action du Super Admin sur son propre compte.
  • Avenant 3 — journal & audit — /api/v1/admin/audit n'expose qu'un @Get() : POST, PATCH et DELETE reçoivent 404, aucune méthode d'écriture n'étant déclarée dans le controller (RG26) ; filtres ?role=&severite=&cible= testés ; réservé au Super Admin par AuditGuard — 403 pour tout autre rôle.
  • Avenant 3 — blog — dépôt d'un article requiert blog_actif = true sur le compte, sinon 403 ; un auteur non admin ne peut appeler /admin/articles/{id}/decision (ArticleGuard, 403) ; l'approbation purge la clé de cache articles:public — vérifié par un espion Jest sur le CACHE_MANAGER injecté.
  • Avenant 3 — CMS — FAQ : le réordonnancement PUT /admin/faq/ordre renumérote de façon contiguë même si la liste envoyée est trouée ; PageCms : blocs typés par DTO imbriqués (@ValidateNested — histoire, mission, 3 valeurs, coordonnées) : 422 sur un bloc manquant ou de mauvais type ; badges de plateforme (/admin/etablissements/{id}/badges) refusés au client s'ils sont poussés en payload de proposition de fiche — le forbidNonWhitelisted du ValidationPipe les rejette en 422 (RG27).
  • Validation — 422 : consentement manquant (RG09), note hors 1–5 (RG06), formule hors énumération / tarif manquant hors essai gratuit (RG13, RG14), téléphone marocain invalide, passage d'un lead à perdu sans raison ou score hors bornes 0–10 (RG21, RG22), rôle inconnu ou role_id inexistant pour la création d'un compte (RG25) — messages français portés par les décorateurs class-validator des DTO.
  • Throttling — 429 au-delà des plafonds (avis / demandes 5 par heure et par IP, login et reset-password 5 par minute — livrable 11 §5), Redis nettoyé entre chaque suite via FLUSHDB sur la base 15 (base dédiée aux tests, jamais la 0 de production).

2.3 — Concurrence

Trois suites dédiées, exécutées sur MySQL avec deux instances PrismaClient distinctes et deux connexions simultanées — un rollback masquerait le comportement de verrou FOR UPDATE, seule voie qui matérialise les garanties des livrables 10–11 :

  • Double comptage de vue à une unité du plafond (RG12) — deux appels comptabiliserVue() concurrents sur la même période : une seule transaction incrémente jusqu'au plafond, l'autre est ignorée ; aucune ne dépasse ; le job BullMQ plafondAtteint est déclenché exactement une fois.
  • Double numérotation de facture à la même seconde (RG14) — FacturationService appelé en parallèle, deux numéros consécutifs F2026-NNNNNN, jamais identiques, aucun trou.
  • Double dépôt de proposition de fiche (RG27 — avenant 3) — deux appels FicheProposalService.submit() concurrents sur le même établissement : la première crée la proposition en_attente, la seconde est refusée par ConflictError("proposition_deja_en_attente") — l'unicité repose sur un verrou de ligne, l'index unique partiel n'existant pas en MySQL 8 (livrable 10 §2.12).

3. Tests front-end (Vitest + React Testing Library + MSW)

  • Formats fr-MA (src/lib/formats.ts) — virgule décimale (★ 4,8), espace fine des milliers (8 420), « 2 500 MAD/mois », dates fr-MA : testé exhaustivement — c'est la vitrine des conventions du produit.
  • Formulaires — demande de contact : bouton inactif sans consentement (RG09), erreurs 422 re-projetées champ par champ sur les Input du design system via setError, double soumission impossible via l'état isPending de la mutation ; dépôt d'avis : note obligatoire 1–5 (RG06) ; réponse à un avis : 409 reponse_existante affiché tel quel (RG07) ; proposition de fiche : la mutation React Query useSubmitFicheProposal poste sur /mon-espace/fiche/propositions et le 422 du ValidationPipe remonte aux inputs (RG20, RG27).
  • Client d'API — apiFetch (fetch() même origine + cookie de session Passport + en-tête CSRF, livrable 12 §4) : 401 déclenche redirectToLogin, 403 affiche un toast d'erreur, 409 un toast d'avertissement avec le message serveur (plafond_vue_atteint, facture_non_payee…), 429 un toast neutre — testés avec des handlers MSW qui reproduisent le format d'erreur du livrable 11 §1.
  • Gardes et navigation — après POST /auth/login, redirection par rôle (RG04, livrable 12 §3) ; SidebarNav du secrétariat filtrée par portées (nav réduite Tableau de bord · Demandes · Fiches) — section retirée = route protégée par la garde de surface côté front et par le ScopesGuard côté API (RG05).
  • États d'interface — Skeleton au premier chargement puis données ; EmptyState avec action ; ProfileUnavailable quand l'API renvoie une fiche sans formule active (RG13) ; badge « Sponsorisé » rendu pour les fiches servies en tête (RG19) ; kanban CRM (liste dense v2 CLAUDE.md 4e passe) : chips d'étape avec compteurs, barre de score /10, badge de température, flèche « Avancer » — boutons Supprimer / Exporter absents du miroir secrétariat (RG23).
  • Avenant 3 — nouveaux écrans — bandeau « Activez votre blog » quand blog_actif = false (US-E18, US-C05) ; éditeur d'article : uploadeur d'image (drag & drop, aperçu dataURL, remplacer / retirer), soumission → statut en_attente, aucun bouton de publication directe ; écran « Vérifier une modification de fiche » : DiffPanel avant / après, aperçu profil avec champ surligné vert, actions Approuver / Modifier / Refuser (RG20, RG27) ; écran Journal d'audit : chips par rôle et sévérité, tableau paginé — aucun bouton d'écriture, aucun contrôle de suppression (RG26) ; centre de notifications role-aware sur la cloche de l'en-tête (CLAUDE.md 4e passe).
  • Hooks de données — invalidations du livrable 12 §4 : traiter une demande rafraîchit compteurs et KPIs ; marquer une facture payée rafraîchit abonnement et débloque Valider / Réactiver (RG14) ; approuver une proposition invalide ['propositions-fiche'] et purge la clé API fiche:{slug}, si bien que le rendu SSR suivant sert la fiche à jour (RG20, RG27) ; approuver un article purge articles:public ; déplacer un lead ou ajouter un suivi invalide ['leads'] et recalcule le bloc CRM du dashboard et les badges de nav (RG21).

6. Exécution et qualité continue

  • En local — docker compose -f docker-compose.test.yml up -d (MySQL 8 + Redis 7 isolés), puis pnpm --filter api test (Jest — unitaires + Supertest), pnpm --filter web test (Vitest + RTL + MSW), pnpm test:e2e (Playwright headless), pnpm lint (ESLint + Prettier + TypeScript --noEmit). ESLint et Prettier tournent aussi en pré-commit local via husky + lint-staged.
  • En CI (GitHub Actions, détaillée au livrable 14) — à chaque push et chaque pull request :
    • job api — services mysql:8 + redis:7, pnpm install --frozen-lockfile, pnpm prisma migrate deploy, pnpm db:seed, pnpm --filter api test:cov --coverageThreshold=90 (Jest + Supertest).
    • job web — pnpm lint, pnpm --filter web test --run, pnpm --filter web build — vite build échoue si type ou import cassé ; côté API, nest build joue le même rôle.
    • job e2e — chaque nuit et avant toute mise en production, contre le staging conteneurisé re-seedé (pnpm playwright install --with-deps puis pnpm test:e2e).
    • job images — exécuté après et seulement après le succès des jobs précédents : construction des images ecoles360-api et ecoles360-web et publication sur ghcr.io, taguées par SHA de commit — une image existe donc si, et seulement si, ses tests sont passés (livrable 14).
  • Politique de blocage — aucun merge vers main si un test échoue ou si la couverture des services passe sous les seuils (§1) ; un bug corrigé = un test de non-régression ajouté, référencé dans le commit.
  • Traçabilité — la matrice du §5 est l'entrée de la recette : chaque scénario du livrable 15 cite les RG couvertes, chaque RG reste couverte à au moins deux niveaux de la pyramide.

Prochaine étape — Livrable 14 : déploiement et CI-CD (production conteneurisée en Docker Compose sur VPS Hostinger KVM 2 sous Ubuntu 24 LTS — api, worker, scheduler, web, mysql, redis, nginx —, images construites en CI et publiées sur ghcr.io, déploiement et rollback par tag, sauvegardes externalisées, PRA RPO 24 h / RTO 4 h).
