Architecture technique

Stack retenue (API NestJS 10, front React 18 + Vite en SSR ciblé, Prisma sur MySQL 8, Passport + session Redis, BullMQ), découpage en modules métier, contrat API, sécurité, et topologie de production conteneurisée en Docker Compose sur VPS Hostinger.

Version 2.5 · Septembre 2026 · S'appuie sur les livrables 1 à 6 et sur les Avenants 1 & 3 · Prépare le livrable 8 (Merise conceptuelle inchangée) et cadre les livrables 10 à 14

1. Stack retenue et justification

La version 2.4 décrivait une application Next.js 14 unifiée. Cette désignation était erronée : le besoin exprimé est celui d'un back-end de service structuré, rôle tenu par NestJS 10. NestJS ne produisant pas de HTML, le front redevient une application distincte — React 18 + Vite — comme aux versions 2.0 à 2.3. Le reste de la pile (Prisma, MySQL 8, Redis 7, BullMQ, les douze services métier, les règles RG01 à RG27) est conservé à l'identique.

Services externesWhatsApp (liens wa.me), SMTP (Nodemailer), OpenStreetMap + LeafletSans coût de licence ; conformes aux usages marocains identifiés au livrable 1.

Décision de rendu du front — le SSR est activé route par route sur le seul site public parce que le référencement des ~8 000 fiches (RG03) exige un HTML complet côté serveur, là où les trois back-offices, authentifiés et non indexables, n'en retirent aucun gain et conservent le coût minimal d'une SPA. Les deux modes cohabitent dans le même dépôt front (web/), partagent le design system et le client HTTP, et sont servis par un unique conteneur web.

Alternatives écartées : Next.js 14 unifié (retenu par erreur en v2.4 — un framework de rendu ne répond pas au besoin d'un back-end de service modulaire ; corrigé ici), Laravel 11 + Sanctum + SPA (stack v1.0, deux langages), Express nu (ni modules, ni injection de dépendances, ni pipeline de validation — tout serait à rebâtir), pré-rendu statique complet du site public à la build (incompatible avec 8 000 fiches mises à jour en continu), Vercel et l'hébergement managé (imposeraient de revoir le PRA du livrable 14 — sauvegarde MySQL externalisée, pas de contrôle de l'OS).

Figure 1 — Topologie de production : sept services Docker Compose sur un même VPS. api, worker et scheduler partagent une image identique et ne diffèrent que par leur commande de démarrage ; mysql et redis conservent leur état dans des volumes nommés ; seul nginx est joignable depuis l'extérieur.

La conteneurisation isole les runtimes ; l'indépendance fonctionnelle entre parties du site vient des modules NestJS — un module par domaine métier, avec son controller, son service, ses DTO et ses guards. Les deux mécanismes sont complémentaires et c'est leur combinaison qui permet de modifier une partie sans toucher aux autres.

3. Découpage back-end — modules NestJS

ecoles360/ ├── api/ # NestJS 10 — image ecoles360-api │ ├── src/main.ts # bootstrap, setGlobalPrefix('api/v1'), ValidationPipe, Swagger │ ├── src/app.module.ts # imports des modules métier + ConfigModule, BullModule, ScheduleModule │ ├── src/modules/<domaine>/ # etablissements · fiches · abonnements · facturation · commissions │ │ ├── <domaine>.controller.ts # prospects · leads · avis · contacts · articles · cms · audit · auth · users │ │ ├── <domaine>.service.ts │ │ ├── dto/ # class-validator + class-transformer │ │ └── guards/ # guards spécifiques au domaine │ ├── src/common/ # guards · filters · interceptors · decorators (@Roles, @Scopes) │ ├── prisma/ # schema.prisma, migrations, seeders (livrable 10) │ └── Dockerfile # multi-stage → node:20-alpine, non-root, HEALTHCHECK ├── web/ # React 18 + Vite — image ecoles360-web │ ├── src/pages/{public,espace,admin}/ # public = SSR ciblé, espace + admin = SPA │ ├── src/components/ · src/api/ · src/hooks/ │ └── Dockerfile # multi-stage → serveur SSR public + assets ├── docker-compose.prod.yml · docker-compose.staging.yml └── docker-compose.dev.yml · docker-compose.test.yml
  • Anatomie d'une requête : Controller (route, @Roles(), décorateurs Swagger) → ValidationPipe (DTO class-validator) → Guard (session, rôle, portée) → Service (transactionnel) → Interceptor de sérialisation (enveloppe {data, meta, links}). Les controllers restent fins ; aucune logique métier n'y vit.
  • Services métier — les 12 services sont conservés à l'identique dans leur sémantique et leurs noms, devenus des @Injectable() exportés par leur module : ViewBillingService (RG12), FacturationService (RG14), SubscriptionService (RG13), CommissionService (RG18), ProspectService (RG17), LeadService (RG21, RG22), ReviewModerationService, ContactRequestService, FicheProposalService (RG27), ArticleWorkflowService (RG27), AuditService (RG26), CmsService.
  • Autorisation : un SessionGuard global résout la session Passport et attache {userId, role, permissions[]} à la requête ; RolesGuard et ScopesGuard lisent les métadonnées posées par @Roles() / @Scopes(). Les portées secrétariat (fiches / contacts / avis) sont vérifiées côté serveur à chaque requête, jamais seulement côté interface (RG23, RG25).
  • Erreurs : un HttpExceptionFilter global traduit toute exception métier en {code, message, details} français — 401 / 403 / 404 / 409 / 422 / 429 inchangés par rapport à la v2.4.
  • Facturation à la vue (RG12) : la vue sponsorisée est enregistrée dans une transaction Prisma $transaction avec $queryRaw … FOR UPDATE sur la ligne de paiement à la vue ; le plafond atteint interrompt le comptage et déclenche l'alerte.
  • Files et planification : les producteurs vivent dans les modules métier (@InjectQueue), les consommateurs sont des classes @Processor exécutées par le conteneur worker ; les tâches récurrentes sont des méthodes @Cron exécutées par le conteneur scheduler — un seul exemplaire de chacun, ce qui exclut toute double exécution.
  • Journal d'audit (RG26) : un AuditInterceptor et l'extension Prisma $extends d'AuditService alimentent audit_logs à chaque action sensible (validation, suspension, modération, permission, publication CMS) ; l'écran Journal du back-office admin (Avenant 3) lit ces entrées.

4. Découpage front-end — React 18 + Vite, SSR ciblé

  • Un dépôt, deux modes de rendu — web/src/pages/public/ est rendu côté serveur par Vike (HTML complet, balises meta et schema.org LocalBusiness par fiche, hydratation ensuite) ; web/src/pages/espace/ et web/src/pages/admin/ sont une SPA classique servie par le même conteneur. Le basculement est déclaré par route, pas par application.
  • Client HTTP — src/api/client.ts appelle /api/v1/* en same-origin avec credentials: "include" ; nginx route /api vers le conteneur api et tout le reste vers web, ce qui évite le CORS et permet au cookie de session de rester SameSite=Lax.
  • État serveur — TanStack Query (React Query) porte le cache, les états de chargement et les invalidations après mutation ; en SSR, les données sont préchargées côté serveur puis déshydratées dans le HTML pour éviter un aller-retour au premier rendu. Aucun store global lourd.
  • Design system — src/ds/ reprend les tokens CSS et les 46 composants documentés (Button, Input, Badge, DataTable, SidebarNav, ReviewCard, PricingCard…), chargés par le bundle unique _ds_bundle.js comme dans les maquettes.
  • Écrans interactifs — listes CRM filtrables, éditeur de blog, page profil éditable (galerie, carte cliquable, FAQ réordonnable), centre de notifications et modales restent des composants client ; ils appartiennent aux back-offices et ne sont donc jamais rendus côté serveur.
  • Performance — découpage de bundle par route (React.lazy), images redimensionnées servies par l'API, pagination systématique des listes (RG05 : 18 fiches / page).
  • i18n-ready — chaînes centralisées dans src/i18n/ et propriétés CSS logiques ; l'arabe (RTL) reste flagué pour la phase 2 (design system).

5. API — conventions et endpoints principaux

API REST versionnée /api/v1 (préfixe global posé dans main.ts) ; JSON, enveloppe standard {data, meta, links} produite par un interceptor, pagination (page, per_page), erreurs normalisées {code, message, details} en français (422 validation, 401/403 auth, 404 introuvable, 409 conflit métier, 429 rate limit). La spécification OpenAPI est générée depuis les DTO et publiée sur /api/docs. Le contrat détaillé est produit au livrable 11.

6. Sécurité et conformité

  • HTTPS obligatoire (TLS 1.3 · certificats Let's Encrypt renouvelés par certbot sur l'hôte et montés en lecture seule dans le conteneur nginx) ; cookie de session HttpOnly / Secure / SameSite=Lax ; protection CSRF double-submit sur toute mutation POST / PATCH / PUT / DELETE.
  • En-têtes de sécurité posés par helmet côté API et par nginx côté front : Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options, Referrer-Policy, Permissions-Policy.
  • Mots de passe hachés Argon2id ; rate limiting Redis (@nestjs/throttler avec stockage Redis) sur login, dépôt d'avis et formulaires publics ; verrouillage progressif après échecs ; réinitialisation par e-mail (jeton password_reset_tokens, TTL 1 h) avec révocation immédiate des sessions actives dans Redis.
  • RBAC côté serveur : rôles superadmin / commercial / secrétariat / établissement + permissions granulaires (RG23, RG25) vérifiés par les guards du module concerné, jamais par le seul affichage.
  • Validation systématique par DTO class-validator et ValidationPipe global en mode whitelist + forbidNonWhitelisted ; uploads contrôlés (type MIME, poids max 5 Mo, re-encodage sharp — retrait EXIF).
  • Surface d'exposition réduite par la conteneurisation : MySQL et Redis ne publient aucun port sur l'interface publique (bind 127.0.0.1, réseau interne Docker) ; les images applicatives tournent en utilisateur non-root ; le pare-feu hôte n'ouvre que 22 / 80 / 443.
  • Loi 09-08 (CNDP) : consentement explicite sur les formulaires parents, finalité déclarée, registre des traitements, purge / anonymisation à 12 mois via BullMQ (RG16), droits d'accès et de suppression exposés côté back-office, minimisation des données collectées.

Le déploiement d'un seul composant se fait par docker compose up -d --no-deps api : l'API est remplacée sans toucher au front, à MySQL, à Redis ni à Nginx. C'est l'expression opérationnelle de la règle énoncée au §2 — les conteneurs isolent les runtimes, les modules NestJS isolent les domaines métier.

8. Flux clés (séquences)

  1. Recherche (SSR) — le serveur de rendu du conteneur web reçoit /etablissements?…, appelle GET /api/v1/etablissements sur le réseau interne, produit le HTML (fiches sponsorisées marquées mais jamais exclusives — RG19) puis l'hydrate ; la barre de filtres met ensuite l'URL à jour côté client.
  2. Contact — le formulaire de la fiche poste sur POST /api/v1/etablissements/:slug/demandes-contact ; le DTO valide le consentement 09-08, ContactRequestService enregistre la demande, émet les jobs BullMQ mail et alerts, et React Query invalide la liste des demandes du back-office.
  3. Vue sponsorisée — POST /api/v1/etablissements/:slug/evenements ; le service ouvre une transaction Prisma, incrémente le compteur de vues sous verrou de ligne, déclenche l'alerte de plafond (job BullMQ) ; au plafond, la vue n'est plus facturée (RG12).
  4. Modération — l'admin décide dans l'écran Avis ; ReviewModerationService publie ou rejette, recalcule la note moyenne dans la même transaction, journalise l'action (RG26) et notifie l'établissement (BullMQ). Le cache Redis de la fiche est invalidé.
  5. Proposition de fiche (RG27) — l'établissement soumet un diff ; FicheProposalService stocke le payload et le comparatif, refuse un second dépôt en attente (409) ; l'admin approuve ou modifie dans l'écran de vérification, la publication invalide le cache public et laisse une entrée d'audit.

Ces flux fixent les invariants que la modélisation des données doit garantir — la Merise (livrable 8) reste inchangée dans sa dimension conceptuelle (MCD, MLD, MPD), le livrable 10 traduisant le MPD en schema.prisma.
